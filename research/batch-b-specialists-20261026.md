## Ticket 03 - one customized specialist per role
- **Singleton.** `core.create_agent` takes one SQLite write lock (`BEGIN IMMEDIATE`) around the role/name check, the profile write and the registry insert. The server and every Hermes worker are separate processes, so concurrent requests serialize there; the second gets `role_exists` with the existing `agent_id` and the instruction to use that specialist's chat and Customize. Nothing is overwritten, no second profile is made, and a profile half-written by a failed request is removed. No production bypass.
- **Optional custom skills.** `skills` omitted, `null` or `[]` = the role's baseline skill plus customized instructions. Supplied skills keep every validation (name, 40-8000 characters, no baseline duplicate, at most 3, unique names), now in `core.validate_skills`.
- **Usable tool selections.** `ROLES[role]["requires"]` names the prerequisites that are real tool contracts (each needs ids another tool returns in the same request): marketplace_search needs _locate, _item needs _search, _photo needs _item, save_listing_draft needs read_catalogue; fb_ad_detail needs fb_ads_search, fb_ad_image needs fb_ad_detail, save_ad_research needs fb_ads_search; generate_flyer needs read_catalogue and inspect_image, inspect_flyer and finalize_flyer need generate_flyer, review_flyer needs inspect_flyer. An incomplete selection is refused as `tool_dependency` naming what is missing; nothing is added silently and no tool is invented. Mandatory tools (read_company_context, memory, skills) are always granted; another role's tool is still `tool_not_permitted`.
- **Main's contract.** The `create_agent` description and schema (skills no longer required, "at most one specialist per role", `role_exists`, dependency list), the role creation guidance, `scripts/setup.py`'s main SOUL and the routing context all say the same. (An existing runtime's saved main session keeps its old prompt until the refresh below runs once.)

## Ticket 04 - customize the existing specialist through its own chat
- **Operator authorization.** The chat box of a specialist has a small **Customize** checkbox. It sends `customize: true` for that one message; the server accepts it only for a specialist (400 `customize_not_available` for main or a non-boolean, 404 unknown agent) and passes it to the worker. Only then is the `customize_specialist` tool offered at all (its toolset `ecom_customize` is added for that turn only), a trusted context note describes what may change, and `turn_state.customize` is true. A model that merely wants more tools, or a message that quotes the trusted wording, changes nothing: the tool is absent, and its handler and Hermes veto hook also refuse without the flag. No classifier, dashboard or main round trip.
- **Operation.** `core.customize_agent(agent_id, changes)`: a partial update of `objective`, `instructions`, `skills` (add or replace by name), `remove_skills` (custom ones only), `add_tools` and `remove_tools` (optional tools from the role's eligible list; same permission and dependency rules as creation; mandatory tools and not-granted removals refused). Anything else (`name`, `role`, `agent_id`, `company_id`, context refs, approvals, `granted_tools`, provider, model, credentials, limits, posting...) is `forbidden_field` and the whole request is refused. Registry row, SOUL.md (rebuilt by the same `build_soul`, so the fixed responsibilities and platform limits stay), custom skill files and an `agent_config_log` row change together or not at all; the baseline skill and the agent's own Hermes-made skills are never touched.
- **Removed tools are refused by the backend.** Every specialist tool handler checks the live registry (`core.is_granted`) and a `pre_tool_call` hook blocks ungranted tools, so a stale schema or a model that still calls a removed tool gets `tool_not_granted` and no research call happens.
- **Effective configuration.** Hermes reuses a saved session's stored system prompt and pinned tool list. The worker computes a stamp (SOUL.md, skill files, toolsets) and, when it builds a fresh agent and the conversation's last stamp differs, clears only that session's stored prompt and pinned tool names (`db.update_system_prompt(sid, None)`, `update_session_tool_names(sid, None)`) and the skills-index cache; Hermes then rebuilds from the current SOUL, skills and tools. Messages, private memory and the session id are untouched. It runs between turns: the customization turn itself keeps running on the old configuration and is never stopped; the next message starts a fresh worker (toolset change) or rebuilds the agent (about 10-20 s). On an existing runtime the first turn of each profile after this change also rebuilds its stored prompt once (history kept); that is what refreshes main's stale prompt.
- **Inspector.** `GET /api/agents/<id>` now also returns `customizations` (time, request id, applied values); the existing inspector shows objective, instructions, skills and tools, and the page re-reads it after a Customize message.

## Applied configuration examples (from the scripted run)
- Objective only: `{"objective": "Compare Acme Linens quilts with Dallas Marketplace listings and report price gaps to the merchant weekly."}` -> `applied` = that objective only; instructions, skills, grants, id, role, name, company and conversation unchanged.
- Instructions + skill: `{"instructions": "... Answer in short ZEBRA-STYLE bullet points, quote prices in USD ...", "skills": [{"name": "price-tier-review", ...}]}` -> the next turn's system prompt contains the new instructions, the new objective, the skill name and the memory note `PURPLE-OTTER`, and no longer the old instructions.
- Tools: `{"remove_tools": ["marketplace_photo"]}` -> stored grants lose it, the next turn's tool list lacks it (the other granted tools remain), a direct call returns `tool_not_granted`; `{"add_tools": ["marketplace_photo"]}` restores it. Refused: `{"remove_tools": ["memory"]}` (mandatory), `{"add_tools": ["fb_ads_search"]}` on the analyst (other role), `{"remove_tools": ["marketplace_locate"]}` while search is still granted (dependency).

## Remaining limitations
- Real-model behaviour unverified: whether main chooses good company-specific objectives/tools, and whether a real specialist calls `customize_specialist` correctly in Customize mode (the tool schema and the trusted context describe the contract; the backend validates everything regardless).
- Customize mode is a per-message checkbox in the temporary UI, not a settings screen; the model drafts the change, the operator reviews it in the inspector afterwards (there is no preview/undo; the log keeps what was applied).
- `skills` replaces or adds by name and refuses a name that collides with the agent's own Hermes-made skill; the specialist's own memory is never edited or cleared.
- Changing tools restarts that specialist's worker on its next message, and a changed prompt costs one prefix-cache rebuild: expect a 10-20 s first reply after customizing.
- Context-section grants (`company_context_refs`) are not customizable (not in the ticket); shared company facts stay main-owned.
- One flyer-prerequisite choice is stricter than the older documentation: `generate_flyer` needs `read_catalogue` and `inspect_image` (the creation guidance already said to request them together).
- `routing_e2e_mock` (needs the local Laya model) and the v2_06 demo runner tests were not rerun (not touched by this batch; they use their own project copies).

## Exact demonstration steps (existing demo runtime or a fresh copy)
1. Back up `runtime/` first if it holds data you want to keep. Start `.\run.bat`, open http://127.0.0.1:8800. A fresh install shows the onboarding start card: finish onboarding (batch A) first.
2. In the main chat ask: "Create a market analysis specialist for competitor pricing" (or a social-media specialist). Main reads the company context, chooses objective, instructions and tools, and creates it with zero extra skills. Ask again for the same role: main answers that the specialist exists (`role_exists`) and points to its chat.
3. Select the specialist in the sidebar. The inspector shows the generated objective, instructions, granted tools and baseline skill.
4. Tick **Customize** under the message box, type e.g. "Make your answers short bullet points that quote prices in USD, and add the Facebook Marketplace search tools", and press Send. The specialist calls `customize_specialist`; the reply lists what the backend applied or refused, and the inspector refreshes to the saved values.
5. Untick (it unticks itself) and ask an ordinary question: the first reply takes 10-20 s (worker rebuilt) and follows the new instructions; earlier messages and memory are still there. Ask it, without Customize, to "give yourself the flyer tools": it cannot (the tool is not offered and the backend refuses).
6. Restart the app: the inspector and the next reply still use the customized configuration.

## Review corrections (2026-10-26, after research/batch-b-review-20261026.md)
Status: both findings corrected, uncommitted, implementation complete, awaiting direct Codex verification. Scripted model only; isolated copies, temporary profiles, no credentials, no live call, real runtime untouched. Real-model behaviour of creation and of a customize turn remains unverified.

**1. Skill removal is truthful (app/core.py `customize_agent`).** Before: the registry/log were committed first, then `shutil.rmtree(..., ignore_errors=True)` ran; a read-only custom `SKILL.md` (Windows) survived, the call returned ok, the registry no longer listed it and re-adding the name failed with `skill_name_taken`. Now a removed skill is first MOVED (atomic rename, which also works with a read-only file inside) to `<profile>/.customize-staging/<id>/`, outside `skills/`, so Hermes cannot load it; then SOUL.md and any new skill files are written; then the registry row and log row are committed. Any failure at any step rolls everything back (database, SOUL.md bytes, skill files, newly created folders, staged folders moved back) and returns `customization_failed`; if a restore step itself fails the error says so. After success the staging folder is deleted best-effort (read-only files included); anything left is outside `skills/`, never loaded, and retried at the next customization under the write lock. A rename failure (for example a locked file) fails explicitly with the previous state intact. Baseline skills, the agent's own skills, memory, history and other profile files are never touched.

**2. Native `skill_manage` is bounded (app/hermes_plugin.py `_skill_guard`, called from the specialist's `pre_tool_call` hook).** Inspected the installed tool: one call is an `operations` array (create/patch/write_file/remove_file, delete as a sole op, each with its own `name`) or the legacy flat shape; `delete` may carry `absorbed_into`; supporting files use `file_path`; the write-approval gate is off in our configuration. The guard reads the live registry and protects the role's baseline skill plus the registry-managed custom skills of that agent; it refuses the WHOLE call (so a mixed batch applies nothing) when any operation, the outer default `name`, `absorbed_into` or a supporting `file_path` segment names a protected skill (names compared case-insensitively on their last path segment, `/` and `\` spellings), or when the call's shape cannot be read (non-list `operations`, non-string names, `..` or absolute paths). Customize mode is not an exception: the only path is `customize_specialist`. The agent keeps full native control of its own other skills and can read skills (`skill_view`, `skills_list`). No Hermes source change, no approval dashboard, `skill_manage` stays enabled.

**Evidence.** `tests/specialist_config_test.py` is now **37/37** (T05-1..9 added). On the unfixed code (`.scratch/evidence_corr_red.txt`) T05-2 (read-only removal reported ok), T05-6 and T05-7 (native edit of a managed skill succeeded and the file changed) failed; T05-3..5 failed there as a consequence of T05-2's wrong state.
