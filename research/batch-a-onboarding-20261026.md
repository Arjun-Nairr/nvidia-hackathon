## What it does
- **Ticket 01.** The operator starts onboarding, then enters the prepared demo link `https://northloom-demo.example.com`. The backend resolves it to ONE saved fictional snapshot (`app/demo_snapshots/northloom-demo.example.com.txt`, labelled prepared demo material, consistent with the catalogue: no price, availability, care or goal text). Main reads the snapshot through its real Hermes worker in its own conversation (`onboarding-main`) with NO route, so `create_agent` and `update_company` stay refused. The reply must be one JSON object: a 60-900 character summary and exactly five questions (ids q1..q5, topics, 2-4 distinct options, at least one `goal` question). Anything else is stored as an error and answered 502 `invalid_model_output` / `generation_failed` (retryable by the operator, never automatically). Unknown or malformed URLs get 404 `unknown_source` without a model call or any fetch. The result is persisted; repeating, reloading or restarting returns it without a model call.
- **Ticket 02.** The operator answers every question (a listed option or a write-in) and may add one optional summary correction. Main combines the snapshot and the answers into name/products/customers/brand/competitors; the backend validates and saves them through the existing `core.update_company` (`updated_by` = onboarding). `goal` is ALWAYS the operator's own goal answer (a model-supplied goal is ignored); `website` is the registered demo link. A provenance block separates source facts from operator input and keeps the correction text. Only then is the state `ready`, chat unlocked, and a brief explanation of the two roles shown. No specialist is created: the operator asks main in chat as before.
- **States and gate** (SQLite table `onboarding`, one row): no row = `not_started` (an existing runtime behaves exactly as before) -> `awaiting_source` -> `awaiting_answers` -> `ready`. While a row exists and is not ready, `POST /api/chat/*` (any agent id) and `POST /api/company` answer 409 `onboarding_incomplete`; only the explicit `/api/onboarding/*` operations and reads are allowed. Failed generation, invalid output or a failed save never advance the state.
- **Routes:** `GET /api/onboarding`; `POST /api/onboarding/start`, `/source` {url}, `/answers` {answers: {q1: {choice: i} | {write_in: text}, ...}, correction}.
- **UI:** a plain form in `app/static/index.html` (start card, link field, summary + questions + correction box, completion card with the roles, provenance and the saved fields). The backend owns state; the page only displays it and the company form is disabled while locked.
- **Files:** `app/onboarding.py` (new), `app/demo_snapshots/northloom-demo.example.com.txt` (new), `app/server.py`, `app/static/index.html`, `tests/mock_llm.py` (two scripted onboarding policies), `tests/onboarding_test.py` (new).

## Limitations and findings
- The two onboarding prompts have never run against the real model; JSON compliance of the real subscription model is unverified (the parser tolerates a code fence and a short lead-in; anything else is a recoverable error).
- Onboarding switches main's Hermes worker to its own conversation and back: expect a cold start (about 10-20 s) on the first onboarding call and again on the first chat afterwards.
- There is no cancel, reset or restart-onboarding operation by design. Starting it on a runtime that already has a company overwrites those fields at completion and locks chat until it finishes: back up `runtime/` first (see the earlier backup folders) and start it only deliberately.
- One registered URL, one snapshot, no crawler, upload or snapshot management. The snapshot hash is stored and a changed file after question generation is refused (`snapshot_changed`).
- Not touched on purpose: the specialist-creation contract, Laya, roles, grants, Neon, providers.

## Demo steps
1. Start the app (`.\run.bat`, the normal start-up) and open http://127.0.0.1:8800. Back up `runtime/` first if it holds data you want to keep.
2. Click "Start onboarding" in the left column. Chat is now locked in the backend and hidden in the page.
3. Enter `https://northloom-demo.example.com` and press "Read the site". Main reads the saved snapshot (the notice says it is prepared demo material); wait up to a minute.
4. Read the summary, optionally correct it, answer the five questions (pick an option or write your own; the goal comes from your answer) and press "Save answers and unlock chat".
5. The left column shows "Complete", the two specialist roles and where each saved field came from; the Company panel shows the saved context; chat is unlocked.
6. In the main chat ask for the specialist you want (for example a social-media specialist): onboarding itself created none.
