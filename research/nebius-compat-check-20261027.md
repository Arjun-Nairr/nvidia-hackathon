## Stage 3b in detail

- Attempt 6 (1.08 s): the specialist called `inspect_image` with the neutral id `pic-a41f` (no label says what the photo shows; the prompt does not either).
- Attempt 7 (4.63 s, HTTP 200, 6,621 in incl. **1,104 image tokens as reported by the endpoint** / 918 out): the request carried one `image_url` part inside the **tool-role message** (Hermes' list-type tool content), JPEG 1200x900, 321,459 bytes, **SHA-256 identical to the app's prepared image** (recorded by the proxy as hash only). The endpoint did not reject the format. Its answer, from the endpoint response: a printed textile on a grey surface against a light wall; left border of red, cream and tan stripes with leaf/floral motifs; a large bird in blue and orange; flower clusters; dense floral panel upper right; visible quilted stitching; a red floral border at the bottom; "a color calibration card with grids of color swatches" at the bottom left; it said it could not read any text. Those details (bird, colour chart, grey backdrop) are in no text supplied to the model, so they come from the pixels. My automatic scorer matched all six detail groups. I looked at the photo myself (corner/detail view of the Met chintz appliqué quilt, with a colour checker) and the description is accurate.
- Attempt 8 (4.65 s, HTTP 200, 980 out): a **byte-identical replay** of attempt 7 made by Hermes itself, also answered correctly ("Based on image `pic-a41f`: ... a bird with blue, red and brown plumage ... a two-panel color chart ...").
- Why it failed: Hermes logged `ReadError [WinError 10054]` after receiving ~12 KB of each streamed answer (TTFB 4.9 s, then a constant 18.9 s stall, then reset). The cause was my counting proxy: it wrote the whole buffered streamed reply (~200+ KB for 918 reasoning-heavy tokens) with a single `wfile.write`, which on this Windows machine stalls ~19 s and is then reset. Earlier replies (< ~110 KB) got through, which is why stages 1-3a passed.
- Offline proof (no billable call): `.scratch/repro_proxy.py` reproduced it with the same openai SDK client (`ReadError WinError 10054` after ~24 s); the proxy now writes in 16 KB slices and the same repro delivers 700 KB+ replies in seconds. Self-test S15 fails with the old single write (red: `ReadError ... 10054`, 23.8 s) and passes with the fix (green). That the fix would let the live stage complete is an inference: it was NOT re-tested live (no renewed authorization, allowance spent).

## How the check was bounded (all in `tests/nebius_compat_check.py`)

- A local counting proxy holds the Nebius key; the isolated app and Hermes only get a dummy token and `NEBIUS_BASE_URL=http://127.0.0.1:8862/v1`. The proxy accepts only `POST /v1/chat/completions` for the exact probe model (no other model, no fallback), clamps `max_tokens` to 8,000, refuses requests estimated above 60,000 input tokens, forces `n=1`, serves `GET /v1/models` locally, trips (blocks all further dispatch) on any non-200 or transport failure, and keeps the ledger on disk. After the live incident it also refuses a byte-identical request (below).
- The isolated copy is a temp copy of `app/` and `scripts/` with a fresh `runtime/` (no secrets, no real profiles, memory, history or allowances), synthetic company context, one existing licensed Met photo under a neutral id, `ECOM_CLASSIFIER=off` (so the routing classifier was NOT exercised), `ECOM_ASSUME_EXISTING_RUNTIME=1`, `ECOM_VISION_MODELS=nebius-token-factory:nvidia/Nemotron-3.5-Super-VL` (a diagnostic override, not global verification), explicit `LLM_PROVIDER` / `LLM_MODEL` / `NEBIUS_MODEL`, and a minimal whitelisted environment (no secrets file, no personal auth stores).
- Retries/replay (corrected wording: this reduces automatic retries; it is NOT a guarantee of a single attempt. Hermes' primary-transport recovery replay remains, and only this probe's proxy refuses identical requests): new opt-in `ECOM_SINGLE_ATTEMPT=1` seam in `core.profile_config()` writes `agent.api_max_retries: 1`, `agent.auto_recovery_cycles: 0`, `memory.nudge_interval: 0` into profiles (including specialists created at run time); plus `HERMES_STREAM_RETRIES=0`, a stale-stream timeout above the proxy's 120 s, and the existing `skills.creation_nudge_interval: 0`. Unset, `profile_config()` is unchanged (self-test S13).
- The real project was fingerprinted before and after every run (secrets file, company.json, app.db, auth.json, main config, profile list): unchanged. `secrets/local.env` still says `LLM_PROVIDER=openai-codex`, `LLM_MODEL=gpt-5.6-terra`. No key text appears in any evidence file (scanned).

## Defects found in the touched paths

Fixed (small, with offline coverage):
1. `scripts/check_nebius.py` used `core.DEFAULT_MODEL`, which does not exist, so it crashed whenever `NEBIUS_MODEL` was unset. Now `core.NEBIUS_DEFAULT_MODEL` (self-test S14 red -> green). It still ignores the app's `LLM_MODEL` precedence; left as is.
2. Proxy single large write (above; test harness defect, S15) and proxy replay guard (S16).
3. `ECOM_SINGLE_ATTEMPT` seam (S13) because specialists created at run time otherwise keep Hermes' default 3 retries.
4. `tests/mock_llm.py`: `BIG_REASONING` marker (long streamed reasoning trace) used by `offline-big`.

Reported, not fixed (outside this task's scope):
- **Hermes replays the last request after a transport error even with `api_max_retries: 1`** (`try_recover_primary_transport`: "one last primary attempt", no config switch). When the failure happens after the endpoint already answered, this bills the call twice (attempt 8 here). In production Nebius use this is a real duplicate-billing risk; the replay guard only exists in this probe's proxy. Disabling it would need a Hermes change, which was out of bounds.
- Hermes also probes `POST <base_url root>/api/show` (Ollama-style) at agent start; harmless locally, unverified against the real Nebius host.
- Configuration precedence is unchanged: `LLM_MODEL` overrides `NEBIUS_MODEL`; switching `LLM_PROVIDER` alone would send `gpt-5.6-terra` to Nebius. `NEBIUS_DEFAULT_MODEL` and the `secrets/local.env.template` still name `nvidia/nemotron-3-super-120b-a12b`, which Nebius retires on November 9; not changed because no provider/config change was authorized.
- Hermes assumes a 131,072-token context for this model (name-based catalogue match) while the account listing says 1,048,576. It affects only Hermes' own compression threshold.
- `git diff --check` flags "trailing whitespace" on lines in CRLF files (these are CRs of the repository's CRLF files, not stray spaces).
