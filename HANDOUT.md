## Implementation (first increment)

Runtime: local Hermes Agent v0.21.4 (git install, `%LOCALAPPDATA%\hermes\hermes-agent`, Python 3.11 venv). App runs on that same venv Python, stdlib-only backend. Inference remote: provider `nebius-token-factory` (built into Hermes; `https://api.tokenfactory.nebius.com/v1`, key env `NEBIUS_API_KEY`).

Layout (all under this folder):
- `app/core.py` — single-company storage and validation (`load_company`, `company_status`, `update_company`; saved in `runtime/company.json`, absent until onboarding), `company_lock` (cross-process file lock around every company save), `ROLES` (market_analysis creation guidance, eligible and mandatory tools, approval requirements), `validate_create_agent`, `create_agent` (refused until the company is complete), `read_company_context`, SQLite registry (`runtime/app.db`), `run_turn`. `app/roles.py` holds the predefined analyst foundation (responsibilities + `competitor-analysis-baseline` skill).
- `app/hermes_plugin.py` — Hermes plugin `ecom-agents`: registers `read_company_context` (toolset `ecom_company`) for all profiles, and for `main` only `create_agent` and `update_company` (toolset `ecom_agents`), plus the `pre_tool_call` veto and `pre_llm_call` routing context. Tool descriptions embed the role guidance and eligible tools.
- `app/worker.py` — long-lived worker for ONE profile (`HERMES_HOME=<profile>`): JSON-lines request/response loop (`turn`/`ping`/`shutdown`), protocol on a duplicated stdout fd while Hermes output goes to stderr (`runtime/logs/worker-<agent>.log`). Imports Hermes once and builds the `AIAgent` on the first turn; later turns reuse both, re-resolve credentials (Hermes refreshes expiring Codex tokens there; a changed key is adopted via `_adopt_openai_credentials`) and re-read history from the profile's Hermes `state.db` every turn (so history is neither lost nor duplicated). A turn that raises drops the agent; the next turn rebuilds it from saved history.
- `app/workers.py` — backend-owned lifecycle: one worker process per agent, spawned lazily on first use, reused, turns serialized per worker, signature = (provider, model, toolsets, conversation) so any config change restarts that agent's worker (and re-syncs profile configs) and never silently switches provider. Dead idle worker: replaced on the next request. Died or timed out mid-turn: explicit error stating the turn is NOT replayed; next request starts a fresh worker from saved state. Stopped on server exit (atexit/finally); workers also exit on stdin EOF if the server is killed hard. `GET /api/workers` lists active workers.
- `app/server.py` + `app/static/index.html` — backend (`127.0.0.1:8800`) and plain-JS UI: main chat, company context, agent list, specialist chat, inspector (objective, instructions, tools, approvals, skills, conversation id). Chat API: `POST /api/chat/<id>` {message, request_id} -> result with `ok`, `text`, `activity`, or a structured error `{ok:false, code, error, retryable}`; `GET /api/state` (who is working, main included); `GET /api/chat/<id>` rows carry `activity`. Business rules (busy/duplicate rejection, limits, activity labels and ok/error status) live in the backend; the UI only displays and sends.
- `app/routing.py` (backend routing + Laya client + decision rules), `app/laya_worker.py` (long-lived Laya process, runs under `.venv-laya`, not Hermes' Python), `app/turn_state.py` (per-turn route seen by the Hermes plugin hooks). Laya setup: `python -m venv .venv-laya` then `.venv-laya\Scripts\python.exe -m pip install laya` (Laya 0.4.1, CPU torch, about 0.9 GB; checkpoint cache in `runtime/hf_cache`, about 0.8 GB, git-ignored). `run.bat` is unchanged: the server prewarms Laya in a background thread.
- `scripts/setup.py` (idempotent: profile + plugin + config + main SOUL; never touches company data), `scripts/reset_demo.py` (ONE-TIME demo reset, see below), `scripts/check_nebius.py` (live check), `run.bat`. No company fixture exists in production paths; the test fixture is `tests/fixtures/company_example.json`.
- `runtime/hermes_home` — private Hermes home (git-ignored). Profiles: `main` and one per specialist under `profiles/<agent_id>`. Personal/trading profiles in `%LOCALAPPDATA%\hermes` are untouched (no files read or modified; the project Hermes home is isolated via HERMES_HOME).
- Config/secrets: `secrets/local.env` (git-ignored; template `secrets/local.env.template`). Fields: `LLM_PROVIDER` (`openai-codex` = ChatGPT/Codex subscription for development, or `nebius-token-factory`; nothing else, no fallback between them), `LLM_MODEL` (codex: required, no default, pick from `list_models.bat`; nebius: optional, else `NEBIUS_MODEL`), `NEBIUS_API_KEY`, `NEBIUS_MODEL`, optional `NEBIUS_BASE_URL`. Process env overrides the file (tests only).
- Codex auth: OAuth tokens live only in `runtime/hermes_home/auth.json` (root of the private home; profiles read it from there). Profile configs set `auth.adopt_external_logins: false` so Hermes never reads or refreshes the Codex CLI login (single-use refresh tokens) or other Hermes profiles.
- Provider switch: `core.llm_config()` is the single source; `core.sync_profiles()` (server start + setup) rewrites provider/model in the root and every profile `config.yaml` (other keys kept); `create_agent` writes new profiles from the same config; the worker passes provider/model to Hermes' `resolve_runtime_provider` (keeps each provider's auth and api_mode; codex = `codex_responses`) and refuses to run if Hermes resolves a different provider. `core.llm_problem()` gives the exact fix and is shown in the UI banner and as the chat error.

Design facts worth keeping:
- create_agent: model supplies role, name, objective, instructions, context refs, 1-3 skills, requested tools. App binds company (`ECOM_COMPANY_ID`), validates the request, then grants the validated tools UNIONED with the role's mandatory tools (`read_company_context`, `memory`, `skills`), creates a blank Hermes profile (`create_profile(no_skills=True)`), writes `SOUL.md` (generated objective+instructions+limits), `skills/<name>/SKILL.md`, `config.yaml`, copies the plugin, inserts registry row with state `idle`. Returns agent_id, conversation_id (`conv-<agent_id>`), granted_tools, approval_requirements, state. Errors are `{ok:false, error, code, field, allowed_values, hint}` (codes: unsupported_role, tool_not_permitted, bad_context_refs, bad_skills, bad_skill_name, bad_skill_content, too_short, too_long, bad_name, name_taken, profile_creation_failed).
- Enforcement is in app code: toolsets passed to each turn come from the registry's granted tools; `read_company_context` returns only sections granted to that agent; specialists never see `create_agent`. Granted toolsets: `ecom_company`, `memory`, `skills` (includes `skill_manage`). Web/scrape/email/post/image/schedule tools exist nowhere in this build.
- Hermes behaviours found: (1) `hermes chat -q` one-shot mode hides `skill_manage`, so the CLI is NOT used for turns; (2) Tool Search would collapse plugin tools behind `tool_search` — disabled via `tools.tool_search.enabled: off` in every profile config; (3) memory is snapshotted into the system prompt at session start, so a preference saved mid-conversation reaches the model via history now and via the prompt in any new session, not mid-session (persistent workers keep exactly this behaviour: the system prompt is restored from the session row each turn; refreshing it is still a later candidate). A bundled `hermes-agent` skill appeared in a specialist profile when turns ran through the CLI path, not through the library worker.
- Approval model: specialists get only none-approval tools; publish/post/send/external change and live research are listed as "requires user confirmation / not connected" and no such tool exists.

## Chat usability (2026-10-09; no streaming, no worker/model changes)

Backend (all in `app/server.py`): one accepted turn per agent at a time; the busy check happens BEFORE anything is written, so a rejected request adds no transcript row and runs nothing (409 `agent_busy`, or `duplicate_in_flight` when the same `request_id` is already running). Other rejections: 400 `empty_message`/`invalid_request`, 413 `message_too_long` (8,000 chars), 404 `unknown_agent`; an unexpected exception in the handler returns 500 `internal_error` saying the message may or may not have been recorded. An exception inside a turn is caught and saved as an error row (agent never left 'running'; the lock and state are released in `finally`). `request_id` idempotency: a retry of a request that already COMPLETED returns its stored result with `replayed: true` and runs nothing (so a retried "create a specialist" cannot create twice); failed turns are never replayed and run again on an intentional retry. The store is in memory (last 200, lost on server restart). `activity` = per-tool-call `{tool, label, status ok|error|no result, input, output}`, labels e.g. "Creating specialist", "Reading company context", "Saving to memory" (unknown tools get a humanised name); stored rows keep raw `tools`, so old transcripts show Activity too.

UI (`index.html`): client state is per agent (rows, in-flight request, draft, error, unread), and a response only touches the agent it was sent to; send is guarded synchronously (Enter, repeated key events and button clicks in one tick make one request, IME composition ignored); composer and the Send button disable and show 'Working...' with elapsed seconds only for the busy agent; status pills for all agents come from `GET /api/state` (polled every 2 s), so a page reload during a turn still shows 'working' and picks up the result; a finished reply for another chat marks it 'new reply'. Failures: connection failure shows that completion is UNKNOWN, keeps the text in the composer and reuses the same `request_id` on retry; a backend rejection says it was not saved or run; 5xx/odd HTTP says the message may not have been recorded; agent-level failures say the turn failed and may have partly run. The text is always restored to the composer. Backend-unreachable state shows a banner and clears stale 'working'. Each agent message has a collapsed 'Activity: <readable names>' dropdown; every call has its own collapsed 'Raw details'.

## Laya routing (main chat only; 2026-10-09)

Flow: `server.chat()` -> (duplicate/busy checks as before) -> for agent `main` only: `routing.route()` BEFORE any Hermes call -> outcome. Handled locally with zero Hermes calls: `out_of_scope`, `unsupported_role`, `clarification`, `existing_agent_task` (recommends opening that agent's chat; no cross-agent messaging, never creates). Sent to main: `business_query` and `create_market_agent`, with the ORIGINAL message untouched plus a trusted routing context appended by the Hermes `pre_llm_call` hook (ephemeral: verified not saved in Hermes history). Classifier failure (Laya missing, crashed, timed out) returns an explicit 'Request routing failed, so nothing was sent to the agent' error, saved as an error row, with the message restored in the UI; it never bypasses routing. `ECOM_CLASSIFIER=off` is a test-only seam (used by the older mock suites; recorded as `classifier_off_test_only` in route metadata). Route metadata (outcome, rule, Laya's own probabilities, latency, whether handled locally) is stored in a new `messages.meta` column (added by an ALTER on start; old rows NULL), returned by the API and shown as a collapsed 'Routing' line in the UI.

Enforcement (not instructions): `create_agent` is allowed only when the route says `allow_create_agent` (outcome create_market_agent). Layer 1: Hermes' supported `pre_tool_call` hook returns `{"action":"block", message}` for create_agent otherwise; layer 2: the tool handler itself refuses (`not_permitted_for_request`); default with no route is fail-closed. The worker sets/clears the route per turn, so worker reuse is unchanged (toolsets and agent signature untouched).

Laya interface used: `laya.load("typed-decisions")` (single English fine-tuned checkpoint, loaded once) and `agent.predict(state, questions)` with `choice` (labels + criteria) and `noul` (yes/no P(true)) questions; the returned `probabilities` are reported as-is. The checkpoint itself warns its confidence is over-confident/uncalibrated (one entry's temperature out of range), so the thresholds in `routing.py` are tuned heuristics, not calibrated probabilities.

Final design (after three failed ones, see below): Laya answers small questions on a SHORT state; the previous assistant message is only shown when the request is a short agreement (Laya `agree` P>=0.60) or needs an antecedent (pronoun like 'it' and domain looked unrelated), because a prior 'Created ...' message otherwise drags unrelated replies toward create; domain (business vs unrelated, P unrelated >= 0.60 -> out_of_scope), kind (create_agent / other_request / unclear, create >= 0.50), role (market_analysis vs social_media / email / other_role; market >= 0.40 -> create; other role >= 0.40 and margin >= 0.10 -> unsupported_role; else clarification). Existing agents are identified by a BACKEND name match (full name, id, or distinctive tail like 'competitor analyst') because Laya's own 'which agent' question never preferred 'none' (observed). Mixed requests are caught by classifying each clause (split on ';', 'and also', 'and then', 'as well as', ', and <verb>') separately and asking for clarification when clause categories differ (sentence splits only count if one clause is unrelated). Creation requests of 3 words or fewer ('Create an agent.') ask which kind. Company summary is in the state's 'business' line (first sentence); supported roles are fixed in the ROLE labels; existing agent identities go through the backend name match. History: last 2 turns, 160 chars each, kept separate from `current_request`.

Observed classification results (`tests/route_table.py`, REAL Laya predictions, no Hermes; 36 cases):
- First design (one big 5-label question over a long state with agents/roles/company): 1 of the first 21 cases passed (probabilities were flat, about 5 s per call; aborted). Two-stage design: 17/33 then 18/33. Per-clause tree experiments 19/33 and 16/33. Final hybrid above: 31/33, 32/33, then 35/36 after adding 3 cases that exposed a context-contamination bug (a reply after an out-of-scope message was rescued into business_query; fixed with the pronoun rule).
- Final per group (expected -> actual): create 5/5, contextual yes 3/4, old instruction 2/2, existing agent 3/3, business 5/5, social/email 4/4, unrelated 4/4, after an out-of-scope reply 3/3, ambiguous 3/3, mixed 3/3. The one failure: 'yes please' after [user asked for an Instagram agent, assistant offered a market-analysis one] -> clarification (role market_analysis 0.38 vs social_media 0.31); safe, no unintended creation. 'thanks! what can it do?' after a creation reply is accepted as business_query / existing_agent_task / clarification and now resolves to one of them.
- Caveat: the thresholds and rules were adjusted on these same 36 cases, so 35/36 overstates generalisation. It is a small hand-written table, not a benchmark; ordinary phrasing outside it may land in clarification (the failure mode is conservative) or, less often, in the wrong non-creating route. No classifier was trained.
- Latency (CPU, no GPU): model load 17-34 s on a warm cache (first ever load 76 s including an about 0.8 GB download); per classification, model time median 0.97 s (min 0.67, max 2.2 s; 1 call for most requests, 2 calls for create/agreement paths, 3 for a conjunction request); HTTP round trip for a locally handled message after warm-up 0.8-2.1 s.
